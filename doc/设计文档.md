### 2.2 数据流

1. **发送**：VL 配置表 → 序列号生成 → BAG 调度（就绪判定 + 轮询仲裁）→ 帧组装（以太网头 → IPv4 → UDP → 载荷）→ 校验和与 FCS 预计算 → 连续流式发送。
2. **接收**：按空闲定界捕获整帧 → 静态检查（长度/MAC/类型/长度一致性/填充）→ 第一遍（CRC-32 与 IPv4 校验和）→ 第二遍（UDP 校验和，含伪首部）→ 元数据交冗余管理判定 → 被接受的帧交付载荷。

### 2.3 双冗余网口

| 方向 | 实现方式 |
|---|---|
| 发送 | 同一帧字节流同时送往 A、B 两路，`ready` 取两路相与，保证两路等速同步、内容一致 |
| 接收 | 帧级选路（A 优先，按当前拍 `valid` 组合选择）→ 共享解析通路 → 冗余管理按序列号判定：第一份被接受、第二份判为重复副本丢弃 |

## 5. 关键算法

### 5.1 发送调度与 BAG 整形

ARINC 664 定义 BAG 为**同一 VL 相邻两帧"开始发送"之间的最小时间间隔**，因此：

1. 每个发送 VL 一个 BAG 倒计时器；计时到 0 且不处于"已授权待发送"状态时该 VL 就绪；
2. 就绪 VL 按轮询（round-robin）仲裁，一次授权一帧；
3. **在帧真正开始发送的时刻**（而非授权时刻）按 BAG 重装计时器 —— 若在授权时刻重装，授权到实际开始之间的准备延迟会使下一帧过早开始，实测起始间隔可能小于 BAG（本项目调试中确实出现过，见测试报告缺陷 D3）；
4. 授权仅在帧组装器空闲时发出，并抑制连续两拍授权，保证授权不会被丢弃；
5. 为防止异常情况下 VL 永久阻塞，加入授权看门狗（在途超时强制清除）。

### 5.2 冗余管理判定

每个接收 VL 独立维护 `上次接受的 SN` 与"是否已收到首帧"：

| 条件 | 判定 | 动作 |
|---|---|---|
| 首个帧 | 接受 | 记录 SN |
| SN == 上次值 | 重复副本（A/B 另一份） | 丢弃并计数 |
| SN == 上次值 + 1（255→1） | 正常新帧 | 接受 |
| 其他，按模 256 前向距离 < 128 | 失序但更新（丢帧后恢复） | 接受，计入完整性错误 |
| 其他，前向距离 ≥ 128 | 过期帧 | 丢弃，计入重复与完整性错误 |
| VLID 未配置 | 未知 VL | 拒绝并计数 |

### 5.3 完整性检查

每个 VL 维护最近 16 帧的错误窗口（移位寄存器），窗口内错误数 ≥ 阈值（默认 3）判定该 VL 故障，
输出 `fault_vec` 供 SNMP 上报（对接 SNMP 时只需把该向量映射到 MIB 对象）。

### 5.4 校验和实现要点

- CRC-32：反射多项式 `0xEDB88320`，初值全 1、结果取反，与标准 CRC-32 一致；
- 反码求和：网络字节序两两配对、奇数长度按 RFC 768 末尾补 `0x00`、进位回卷折叠、IPv4 校验和字段参与计算时置 0；
- UDP 校验和覆盖 12 字节伪首部 + UDP 头 + 载荷，结果为 0 时发送 `0xFFFF`。

### 5.5 SNMP v2c 代理（`afdx_snmp_agent.v`）

**协议子集**：BER/ASN.1 解析 `SEQUENCE { version, community, GetRequest[A0] }`，
组包 `SEQUENCE { version, community, GetResponse[A2] }`，原样回显 request-id 与请求 OID；
未知 OID 返回 `noSuchObject(0x80)`；社区名错误、非 GetRequest PDU 一律静默丢弃并计数。

**MIB 对象（10 个标量）**

**网络接入（`afdx_mgmt_path.v`，已完成）**

```
MAC RX 字节流 -> 空闲定界捕获 -> 校验 EtherType/IPv4/UDP 目的端口 161
              -> 提取 SNMP 报文 -> afdx_snmp_agent
              -> 响应载荷 -> 以太网+IPv4+UDP 封装（IP/UDP 校验和 + FCS）
              -> 回填请求方源 MAC/IP/UDP 端口 -> 与 AFDX 帧互斥发送
```

- 地址回填：响应目的 MAC/IP/端口取请求方的源地址，源地址用端系统固定 MAC/IP；
- 发送互斥：管理帧只在 AFDX 帧组装器空闲时发送，避免打断 AFDX 帧；
- 端口过滤：非 161 端口的帧在管理通道内直接丢弃，不影响 AFDX 数据通路。

**当前限制**

1. 仅支持短格式长度（单字节，报文 < 128 字节）——`snmpget` 单 OID 报文满足；
   支持多 OID 的 `GetBulk`/长报文需扩展长度解析。
2. `GetNext`（MIB 顺序遍历）与 `SetRequest`（只读 MIB 统一返回 `notWritable(5)`）已实现；
   `GetBulk` 与多 varbind 请求尚未实现。

**Trap（v2c Trap-PDU，已完成）**

- 触发条件：VL 故障位图 `vl_fault` 发生变化（复位后首次采样不触发）；
- 报文：`SEQUENCE { version, community, A7 { request-id=1, 0, 0,
  varbind-list { sysUpTime.0, snmpTrapOID.0 = 1.3.6.1.4.1.99999.0.1, afdxVlFault.0 } } }`，
  固定 90 字节，短格式；
- 发送：与 GetResponse 共用管理通道封装，回填请求方地址；仅在 AFDX 帧组装器空闲时发送。

### 5.6 ARINC 615A 数据加载（`afdx_load_615a.v`，简化子集）

| 操作码 | 报文 | 行为 | 响应（8 字节） |
|---|---|---|---|
| 0x01 | WRQ + 文件名 | 复位镜像长度/CRC | `[0x81][status][0][0][CRC]` |
| 0x02 | DATA + 块号 + ≤512 字节 | 写入 (blk-1)×512，增量更新 CRC-32 | `[0x82][status][blk][CRC]` |
| 0x03 | ACTIVATE | 锁存 CRC，置 loaded | `[0x83][0][0][0][CRC]` |
| 0x04 | READ | 回读镜像长度与 CRC | `[0x84][0][len][CRC]` |
| 其他 | — | 计错误 | `[op|0x80][2][0][0][0]` |

- 镜像 RAM：8 KB（16 × 512 字节块）；
- CRC-32 与以太网 FCS 同一算法，Python `binascii.crc32` 可直接比对；
- 该模块是"数据加卸载功能"的可演示子集，完整 615A 会话/文件系统语义需按标准补充；
- 网络接入：管理通道已按 UDP 目的端口 10000 分流到加载器。

## 6. 接口约定

### 6.1 MAC 总线（8 位）

| 信号 | 方向（模板） | 本设计语义 |
|---|---|---|
| `tx_data[7:0]`、`tx_valid` | 输出 | 帧字节流；**帧内连续、帧间留空闲**，空闲即帧边界 |
| `tx_ready` | 输出 | 本端"可发送/空闲"指示（帧组装器空闲 = 1） |
| `rx_data[7:0]`、`rx_valid` | 输入 | 对端送来的帧字节 |
| `rx_ready` | 输入 | 外部 MAC 的数据有效限定（与 `rx_valid` 相与后采样） |

> ⚠ 赛题模板中 `tx_ready` 为输出、`rx_ready` 为输入，与 AXI-stream 习惯（`ready` 表示反压）相反。
> 本工程按上表语义实现，并在 `afdx_top.v` 顶部注明；若组委会澄清为反压语义，只需调整该文件的端口连接，
> 不影响内部模块（内部一律使用 `valid/ready` 反压语义）。

### 6.2 赛题模板端口映射

`AFDX_top` 的 8 个端口名称、位宽、方向与指南模板逐字一致；
上电后由内部配置序列写入默认 VL（发送 VLID `0x1001`、BAG 2000 周期、功能数据 32 字节；
接收 VLID `0x1001`），使顶层可独立完成收发，不依赖额外的应用侧端口。

## 7. 时钟、复位与约束

- **时钟**：单时钟域（50 MHz 参考，1 字节/周期），无跨时钟域路径；100 Mbps 对应约 12.5 MB/s，
  总线占用率约 25%，余量充足。
- **复位**：同步高有效复位。
- **时序约束（SDC）要点**：主时钟周期约束；MAC 总线输入输出延迟；因单时钟域，无异步路径需求。
  按赛题指南，eLinx 支持工业标准 SDC 文件。
- **物理引脚约束**：`test.edc` 为 22 个顶层端口分配 CSG484_H 位置。当前位置是合法占位分配；上板前必须替换为目标板卡实际引脚图。
- **约束应用**：引脚位置在 Implementation 中生效，随后 Generate Bitstream；本次最终实现 WNS +1.411 ns。

## 8. 资源与时序

### 8.1 S1/S1b 存储重构结论

### 8.4 S2 发送 VL 扫描结构

- TX VL 表按 VL 低两位交错到 4 个 bank，目标容量 128 VL；
- scheduler 每拍并行检查 4 个 VL，128 VL 一轮 32 拍（640 ns）；
- `next_start` 同样使用 4 bank RAM，帧开始发送时写回 `now + BAG`；
- 就绪 VL 进入 16 深 FIFO，再由轮询授权；
- 授权后同步读出完整 VL 记录，再启动帧组装。

S2 中间档（32 TX VL）最终实现：

| 项目 | 结果 |
|---|---:|
| LUT | **13,079** |
| FF | **3,404** |
| Memory | **54,592 bit / 17 块** |
| WNS（50 MHz） | **+0.805 ns** |
| 约束频率等效 Fmax | **约 52.09 MHz** |
| 布线错误 | **0** |

32 VL 压测共 183 帧，每条 VL 至少 3 帧；BAG 1/2/4 ms 全部满足且无饿死。

### 8.5 S3 接收 RM 状态结构

- VLID 配置表使用同步 RAM，按索引升序配置；
- 每帧执行二分查找，候选命中后同步读取状态 RAM；
- 状态记录包含 last SN、have、16 帧错误窗口和 fault；
- 判定后通过单写口读改写状态；
- 解析器通过 `rm_ready` 等待查找/判定完成。

64 VL 专项压测覆盖首帧、重复、前向恢复、过期、未知 VL 和故障窗口，全部通过。

| LUT | **13,267** |
| FF | **3,523** |
| Memory | **56,384 bit / 19 块** |
| WNS | **+0.870 ns** |
| 约束频率等效 Fmax | **约 52.28 MHz** |
| 布线错误 | **0** |

### 8.6 S4/S5 全容量结构

- RX `fault_vec[N-1:0]` 宽端口取消，改为 `status_req/index/data/ready` 按索引读口；
- 状态口返回 `fault/en`，管理通道轮询前 8 个 VL 形成 SNMP 兼容快照；
- 顶层最终切换为 128 TX VL / 4096 RX VL，模板顶层端口不变；
- RX VLID 表与 RM 状态表分别使用同步 RAM，二分查找后读改写状态；
- TX 使用 4-bank 配置表、32 拍后台扫描和 16 深就绪 FIFO。

容量测试：

- 128 TX VL、BAG 1/2/4 ms 混合：724 帧，每条 VL 至少 3 帧，无饿死；
- 4096 RX VLID：全表首帧与重复帧轮询，accept 4099、dup 4096、OOS 3、
  IC 3、unknown 0，仅目标 VL fault 置位。

| 约束频率等效 Fmax | **约 54.0 MHz** |
| 布线错误 | **0** |

**性能实测（仿真）**：发送引擎满负载（BAG=1、81 字节帧）等效 **130.1 Mbps**；

## 9. 设计权衡、已知限制与待确认事项

### 9.1 已知限制

1. **发送前校验和计算**：为在发送头部前得到 UDP 校验和，帧组装器在发送前对载荷做一遍扫描，
   引入约"1 倍载荷长度 + 60"周期的准备延迟。这不影响 BAG 合规性（起始间隔 ≥ BAG），
   但会放大低带宽 VL 的等待抖动（实测见测试报告）。改进方向：① 应用写入时增量累加校验和；
   ② 校验和/CRC 通路加宽到 4-8 字节/周期。
2. **接收解析为多遍扫描**，最坏约 (帧长 + 载荷 + 功能数据) 个时钟；单帧缓存，解析期间对上游反压。
3. **双网口共用一条解析通路**：两路副本时间上重叠时会丢弃后到者字节（测试中通过给 B 路增加
   大于一帧的传播延迟避免）。量产设计应为每个网口配置独立解析通路。
4. **VL 规模**：接收 VL 查找为并行比较，实际可综合规模受资源限制；4096 个接收 VL 需改为
   哈希/CAM 结构 + 共享缓冲池。
5. 顶层模板未提供应用侧接口，故本工程的"功能数据"由确定式生成公式产生（便于逐字节验证）；
   真实系统应改为分区写入口。

### 9.2 已确认口径（依据项目负责人确认）

1. **ready 语义**：按反压定义。工程内部统一使用 valid/ready 反压；顶层按赛题模板方向映射
   （`tx_ready` 输出为本端可发送指示，`rx_ready` 输入为对端数据有效限定），见 6.1。
2. **硬件平台**：不需要，全部以仿真验证（与指南第四节一致）。
3. **以太网 MAC**：允许自行实现；本工程按 8 位 MAC 总线接口自行实现帧定界、填充与 FCS。
4. **序列号位置**：由本设计决定——放在 UDP 载荷头部 `VLID(2B) + SN(1B)`，便于逐字段核对。
5. **编码规则**：参考公开的 ARINC 664 Part 7 / IEEE 802.3 协议规范；不确定处按本设计文档
   显式约定实现，并在第 3 章给出逐字段说明。
6. **功能口径**：以满足赛题文件给出的功能与性能要求为前提；SNMP 至少 Get + Trap，
   ARINC 615A 与 RTC 时钟同步按指南要求补齐。
