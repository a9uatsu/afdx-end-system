## 3. 实测数据

### 3.1 底层库（V0）

```
用例数=62  通过=62  失败=0      RESULT: PASS
```

覆盖：空输入、单字节、奇数长度、全 0x00、全 0xFF、全 0xFF 双字节进位链、IPv4 头、UDP 头、

### 3.2 发送通路（V1-V5）

帧长实测范围 **64 .. 1517 字节**（要求 64..1518）✅

| VLID | BAG | 帧长 | 帧数 | 起始间隔 min/avg/max | 抖动(间隔-BAG) min/avg/max | 抖动标准差 |
|---|---|---|---|---|---|---|
| 0x1001 | 40.0 µs | 81 | 34 | 40.06 / 61.41 / 119.96 µs | +0.06 / +21.41 / +79.96 µs | 34.90 µs |
| 0x1002 | 240 µs | 1517 | 9 | 240.02 / 240.06 / 240.10 µs | +0.02 / +0.06 / +0.10 µs | 0.021 µs |
| 0x1003 | 120 µs | 64 | 17 | 120.02 / 120.42 / 125.70 µs | +0.02 / +0.42 / +5.70 µs | 1.36 µs |

**结论**：三条 VL 的起始间隔**全部 ≥ BAG**（合规）；0x1002/0x1003 的抖动在 **0.02-5.7 µs**，
远优于"数十微秒"要求；0x1001（BAG 仅 40 µs）的抖动偏大，原因是相邻 VL 中 1517 字节长帧的
"发送前校验和计算 + 发送"占用时间超过其 BAG（非抢占式调度），属**已定位的已知限制**，
改进方向见设计文档 9.1。

## 4. 缺陷记录（本次验证中发现并修复）

> 以下缺陷均在"跑通验证"过程中被**测试发现**，是本次交付最主要的证据之一。

| # | 类型 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| D1 | 验证环境 | 捕获帧长出现 81/143/224 累积 | 同一周期对 `flen` 两次非阻塞赋值，后者覆盖复位 | 显式处理首字节，`flen<=1` 与 `fbuf[0]` 同拍赋值 |
| D2 | RTL | 序列号加到错误的 VL 上 | 递增目标用了"待发 VL"，而它在长帧发送期间可能被新授权改写 | 增加"正在发送的 VL"寄存器 `tx_vl` |
| D3 | RTL | 实测 BAG 起始间隔小于配置值 | 计时器在"授权"时刻重装，授权到实际开始之间还有准备延迟 | 改为在"帧真正开始发送"时刻按 BAG 重装 |
| D4 | RTL | 某条 VL 永久阻塞、帧被丢弃 | 授权信号为寄存器输出，门控出现一拍空窗，两拍内连续授权 | 增加 `!grant` 抑制 + 在途看门狗 |
| D5 | RTL | IPv4 校验和恒判错 | `finalize` 与结果比对在同一拍（少一拍的锁存等待） | 增加锁存等待状态 |
| D6 | RTL | IPv4/UDP 校验和比对全部失败 | 组合函数在连续赋值中调用时敏感度不完整（工具相关，且不利移植） | 改为 `always @(*)` 组合块产生字节 |
| D7 | RTL | 接收帧长恒为 X，全部帧被判错 | `wr_ptr` 为 12 位却用 `wr_ptr[15:0]` 位选，越界位为 X | 改为零扩展赋值 |
| D8 | RTL | 每帧只交付 1 个字节 | 冗余管理的 `accept` 只在元数据那一拍有效，下一拍被清零 | `accept` 保持到下一次判定 |
| D9 | RTL | 双网口时 B 路副本全部校验失败 | 网口仲裁用寄存器选择，晚一拍导致某帧首字节被判到另一路 | 改为按当前拍 `valid` 的组合选路（A 优先） |
| D10 | 参考模型 | 帧长为 82 而非 81 | Python `ip[10:11] = 2 字节` 切片长度不匹配，把 IP 头撑成 21 字节 | 改为 `ip[10:12]` |
| D11 | 测试设计 | "帧长不足/填充非 0"两个错误场景未真正触发 | 构造的帧本身已 ≥ 64 字节且无填充 | 改为截断帧 + 零长度载荷配合非 0 填充 |
| D12 | RTL（**综合阶段发现**） | eLinx Run Synthesis 报 `Can't resolve multiple constant drivers for net "overflow"`（`afdx_frame_rx.v`） | `overflow` 在捕获块与解析块两个 `always @(posedge clk)` 中都被赋值，Icarus 静默接受、综合器判为多驱动 | 只由捕获块驱动：新帧首字节清零、缓冲写满置位；并新增 `scripts/check_multidriver.py` 静态检查，已纳入一键回归 |

> **D12 的意义**：它说明"仿真通过 ≠ 可综合"。后续每次修改 RTL，先跑
> `python scripts\check_multidriver.py test.srcs\sources_1\afdx`，再去综合。

## 6. 结论与遗留问题

**结论**：AFDX 端系统的核心通路与赛题五条功能要求均已实现并通过仿真验证：
通信、高完整性（冗余管理 + 完整性检查）、SNMP v2c（Get/GetNext/Set/Trap）、
ARINC 615A 数据加卸载（简化子集）、RTC 时钟同步。
容量达到 **128 发送 VL / 4096 接收 VL**；最终实现 **14,059 LUT（10%）、3,876 FF、
46 个存储块（4%）**，50 MHz 下 slack **+1.411 ns**，布线 0 错误，BitGen 成功。

**P2 已完成**：22 端口位置约束补齐，最终 placed/routed 实现 WNS +1.411 ns，BitGen 成功。

**P3 遗留优化项（不影响当前验收）**

1. SNMP GetBulk / 多 varbind（当前单 varbind 已满足 Get/Trap 需求）；
2. 真实应用侧数据写入口（当前为确定式数据源）；
3. 双网口独立解析通路（当前共享解析器，副本重叠时后到者丢弃）；
4. 发送前多遍校验和带来的短 BAG 抖动（已量化，见 3.2）。

**可复现性**：全部结论均可用 `scripts\run_all.ps1` 一条命令复现；`sim\work\` 保留原始日志与记录文件。
