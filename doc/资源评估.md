# 128 发送 VL / 4096 接收 VL 容量资源评估

**评估对象**：`AFDX_top`（EQ6HL130 / CSG484_H，eHiChip6）
**评估日期**：2026-11-02
**基线**：eLinx 综合报告（`test.runs/synth_1/test.map.summary`，状态 Successful）

---

## 1. 结论摘要

| 方案 | 128 TX VL | 4096 RX VL | 预计 LUT | 预计内嵌存储 | 可行性 |
|---|---|---|---|---|---|
| A. 直接改参数（现有代码） | 可以 | 不可以 | **约 49k（TX）** | 0 | TX 能动但浪费；RX 状态寄存器就需 176k bit，超过 136k LUT 上限 |
| B. 存储搬进内嵌 RAM + 串行查找/扫描 | 可以 | 可以 | **约 2.5k-3k** | **约 30-35 块（≈290 kbit）** | ✅ 推荐 |
| 中间档（现有代码，局部放大） | 32 个 | 64 个 | 约 15k | 0 | ✅ 一天内可做，适合赶进度 |

**一句话**：发送侧受"每 VL 252 bit 配置表 + 128 选 1 组合读"支配，接收侧受"每 VL 43 bit 状态 + 4096 路并行比较"支配。
不改架构，RX 根本放不下；把表搬进内嵌 RAM 后，两项目标都能轻松放下（用掉不到 2% 的 LUT、6% 的存储）。

## 2. 器件与基线

| 项目 | 数值 | 来源 |
|---|---|---|
| LUT | 136,000 | `device_fpga.xml`：`<LUTs>136000</LUTs>` |
| 内嵌存储 | 4,915,200 bit（≈533 块 9 kbit） | 同上 `<MemoryBits>` |
| DSP | 48 | 同上 |
| PLL | 8 | 同上 |
| **当前综合结果** | **1,271 logic elements，378 寄存器，0 memory bits，0 DSP** | eLinx 综合报告 |

**基线解读**：

1. 1,271 个 LE 中约 1,000 个是**接收帧缓存 `mem[2048][8]`**（16 kbit 被综合成分布式 LUT-RAM，1 个 LUT6 约存 16 bit）。它才是当前面积的主要来源，不是协议逻辑。
2. `Total memory bits = 0` 说明当前**没有任何结构被映射到内嵌 RAM**——所有表都用寄存器/LUT 实现，这正是容量扩展的瓶颈。
3. 协议逻辑本身（CRC、校验和、组帧/解析状态机、调度器）约 250-300 LE，非常轻。

## 4. 方案 A：直接把参数改成 N_VL=128 / N_RX_VL=4096

### 4.1 发送侧（可行但浪费）

| 资源项 | 估算 | 依据 |
|---|---|---|
| VL 配置表寄存器 | 128 × 252 = 32,256 bit | 每 bit 一个寄存器 → 约 32k LE |
| 配置表读多路器 | 252 bit × 128:1 ≈ **10,800 LE** | 128:1 约需 43 个 4:1 LUT/bit |
| BAG 计时器 | 128 × 32 = 4,096 LE | 计时器 + 递减器 |
| 计时器扫描/仲裁 | 约 1,000 LE | 128 路"到 0 且未在途"判断 + 优先级编码 |
| 序列号 | 128 × 8 + 读多路器 ≈ 1,400 LE | |
| **合计** | **约 49,000 LE（36%）** | 能放下，但明显浪费 |

时序：128:1 多路器约 4 级 LUT，配合 32 bit 零检测与优先级编码，50 MHz 下仍有余量（约 4-6 ns），但余量不大。

### 4.2 接收侧（不可行）

| 资源项 | 估算 |
|---|---|
| 每 VL 状态寄存器 | 4096 × 43 = **176,128 个寄存器** → 已超过 136,000 LE 上限 |
| VLID 并行比较 | 4096 × 16 bit ≈ 12,000 LUT |
| 匹配优先级编码 | 约 4,000 LE |
| 完整性窗口（16 bit × 4096，变量索引写） | 65,536 个寄存器 + 约 4,000 LE 选择逻辑 |
| **合计** | **约 25 万 LE，远超器件** ❌ |

**根本矛盾**：器件只有 136k 个"LUT+寄存器"单元，而 4096 个 VL 仅状态就需要 176k bit。**必须用内嵌存储**，这不是优化问题，是硬约束。

### 4.3 中间档建议（若时间紧）

直接参数化到 **32 发送 VL / 64 接收 VL**：

| 侧 | 估算 |
|---|---|
| TX | 32 × 252 ≈ 8.1k 寄存器 + 32:1 读多路器约 2k ≈ **10-11k LE** |
| RX | 64 × 43 ≈ 2.8k + 比较/选择约 1k ≈ **4k LE** |
| 合计 | **约 15k LE（11%）**，50 MHz 可收敛 |

这条路线**只改参数 + 改 TB 配置**，半天到一天可完成，先满足"多条 VL 并发"的演示需求。

## 5. 方案 B：可扩展重构（推荐）

### 5.1 设计要点

| 模块 | 现状 | 改造后 |
|---|---|---|
| `afdx_vl_table` | 寄存器堆 + 128 选 1 组合读 | **单口 RAM 表**，一次读一条记录；调度器/组帧器串行取用 |
| `afdx_scheduler` | 每 VL 一个 32 bit 递减器 + 全并行扫描 | **全局时基 + 每 VL `next_start`（RAM）+ 后台扫描器 + 就绪 FIFO** |
| `afdx_sn_gen` | 独立 128×8 数组 + 组合读 | **并入 VL 表记录**，省掉一路读多路器 |
| `afdx_rm_rx` | 4096 路并行比较 + 变量索引写 | **VLID 表存 RAM + 二分查找（12 拍/帧）+ 读-改-写** |
| `fault_vec` | 4096 bit 宽端口 | 改为**状态读端口**（按索引读） |
| `afdx_frame_rx` 帧缓存 | 2048×8 分布式 LUT-RAM（约 1,000 LE） | 移入内嵌 RAM（4 块），LE 直接省下约 1,000 |

### 5.2 存储预算

| 存储结构 | 深度 × 位宽 | bit | ≈9 kbit 块 |
|---|---|---|---|
| RX VL 状态表（VLID+SN+窗口+标志） | 4096 × 48 | 196,608 | 22 |
| TX VL 配置表 | 128 × 252（精简后 165） | 32,256（21,120） | 4（3） |
| TX 每 VL `next_start` | 128 × 32 | 4,096 | 1 |
| 接收帧缓存（双 bank） | 2 × 2048 × 8 | 32,768 | 4 |
| **合计** | | **约 266 kbit** | **约 31 块（5.8% 存储）** |

### 5.3 逻辑预算

| 结构 | 估算 |
|---|---|
| 现有协议逻辑（CRC/校验和/组帧/解析） | 约 300 LE |
| VL 查找状态机（二分 12 拍） | 约 200 LE |
| 发送扫描器（4 VL/拍，128 个 → 32 拍一轮）+ 就绪 FIFO(16 深) | 约 600 LE |
| 各计数器/状态读口 | 约 300 LE |
| 余量（布线/优化） | 约 1,000 LE |
| **合计** | **约 2,500-3,000 LE（约 2%）** |

### 5.4 时序与吞吐

| 指标 | 评估 |
|---|---|
| 每拍逻辑深度 | RAM 读 + 少量比较/加法，单级 LUT，50 MHz 余量充足（可上 100 MHz+） |
| VL 查找延迟 | 二分查找 12 拍 = **240 ns @50 MHz**（每帧一次） |
| 发送就绪扫描 | 4 VL/拍，128 个 = 32 拍 = **640 ns**；BAG 最小 1 ms，余量约 1500 倍 |
| 解析吞吐 | 1517 B 帧约 4,500 拍 ≈ **90 µs** < 线速 121 µs ✅；64 B 帧约 150 拍 ≈ 3 µs < 5.12 µs ✅ |
| 128 VL @1 ms BAG 带宽自检 | 128 帧/ms × 64 B × 8 ≈ **65 Mbps** < 100 Mbps ✅（帧更大时会自然超订，属配置问题） |

**结论**：吞吐不是瓶颈（现有串行多遍解析器已能跟上 100 Mbps），瓶颈纯粹是"状态存储"和"宽并行比较"。

## 7. 配套验证建议

1. **TX 容量压测**：128 条 VL 全使能、BAG 取 1/2/4 ms 混合，跑 10 万帧，统计每条 VL 的起始间隔最小值与最大抖动，验证无饿死、无丢帧。
2. **RX 容量压测**：生成 4096 个 VLID 的帧轮询送入，检查查找命中率 100%、故障标志按索引读取正确、计数器闭合（接收 = 交付 + 重复 + 拒绝）。
3. **存储占用核对**：综合后看 `Total memory bits` 是否接近本节预算（266 kbit），若远高说明表被实现成寄存器；若远低说明被优化掉。
4. **时序核对**：确认 50 MHz 下 WNS ≥ 0，重点看 RAM 读→比较→写回这条路径。

## 8. 建议决策

1. **现在**：把 128/4096 作为设计目标写进文档，但保留"32/64 可演示版本"，避免重构期间没有可交版本。
2. **优先级**：先做阶段 1（帧缓存进 RAM），单这一步就能腾出约 1,000 LE，且风险最低、回归可完全复用。
3. **若赛题只考察发送 VL 数**：可以直接把 `N_TX_VL` 提到 128（约 49k LE，器件放得下），接收侧维持现有规模，一天内可完成。
4. **若两项都要**：按方案 B 走，约 2 周；关键是把"表"和"状态"全部搬进内嵌 RAM，而不是继续用寄存器堆。
